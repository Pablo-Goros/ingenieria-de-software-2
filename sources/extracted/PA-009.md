## Página 1

### Examen de Ingeniería de Software II — Primer Cuatrimestre 2026

Condición de aprobación: al menos 3 puntos de (c).

Una red de hospitales, que consta de una docena de centros de salud, necesita un sistema centralizado para administrar eficientemente todo su flujo de suministros e insumos médicos, desde la adquisición hasta el momento de su utilización.

El sistema debe mantener un inventario exacto en tiempo real de todos los productos (medicamentos, material descartable, equipamiento) a través de múltiples puntos de almacenamiento, incluyendo el almacén central y los depósitos menores de cada hospital. Cada ítem debe estar asociado a su fecha de vencimiento y número de lote.

La gestión de inventario incluye la función de pedidos automáticos. Cuando el nivel de existencias de un insumo vital desciende por debajo del mínimo de seguridad, el sistema debe generar una solicitud de compra preliminar para el departamento de adquisiciones.

El personal médico y de enfermería utiliza dispositivos en los puntos de atención para registrar el consumo de suministros al aplicarlos a cada paciente. Esta funcionalidad es clave para asegurar la trazabilidad completa del producto desde su ingreso al hospital hasta su uso final.

Para acelerar el reabastecimiento, se requiere que el sistema se comunique con los sistemas de los principales proveedores. Esto permite enviar órdenes de compra directamente y recibir notificaciones de envío, eliminando la necesidad de ingresar datos manualmente.

La gerencia hospitalaria utiliza la plataforma para obtener informes analíticos. Estos reportes detallan los costos de suministros desglosados por hospital, departamento o tipo de procedimiento, y permiten realizar auditorías completas de la cadena de consumo.

### Ejercicio A

1. El sistema debe mantener un inventario exacto en tiempo real.
2. El sistema debe permitir el registro del consumo de suministros al aplicarlos a cada paciente.
3. El sistema debe realizar pedidos automáticamente según el nivel de insumos.
4. El sistema debe comunicarse con los sistemas de los principales proveedores.
5. El sistema debe brindar reportes analíticos a la gerencia.

### Ejercicio B

Los atributos de calidad seleccionados son:

1. **Availability:** el sistema debe ser altamente disponible, ya que las faltas de stock deben detectarse y comunicarse; la falta de un medicamento puede causar fatalidades.
2. **Security:** el sistema maneja stocks y ubicaciones de drogas, en muchos casos no habilitados al público, por lo que es información sensible que se debe proteger.
3. **Interoperability:** se quieren integrar sistemas de distintos proveedores, que pueden variar con el tiempo, para enviar órdenes y recibir notificaciones.
4. **Performance:** el sistema debe mostrar stock de los productos en tiempo real y no puede demorar mucho con las compras para la reposición.

## Página 4

- La cola debe correr en cluster para brindar disponibilidad, tener persistencia de datos y aguardar el ACK de procesamiento del worker para eliminar el dato.
- Los reportes se obtienen de la base de datos SQL OLAP, luego de realizar el proceso ETL a partir de las SQL OLTP.
- Se debe preparar tanto hospitales como depósitos para degradaciones en servicios; por eso se propone contar con generadores y dos proveedores de internet.
- Los médicos realizan el registro a través de dispositivos por medio de una SPA, y los gerentes obtienen sus reportes también a partir de ella.
- Se tiene un endpoint específico mediante el cual el proveedor notifica el envío de los productos, especificando el almacén. El backend actualiza el stock en base al detalle recibido.
- El sistema, específicamente el worker, debe validar que el proveedor tenga stock. Por ende, envía peticiones en paralelo usando multithreading, con un timeout para no esperar infinito. Al recibir respuesta, decide en base a una serie de reglas predefinidas y envía la orden de compra.
- Cada almacén y depósito tiene su propia conexión con el sistema; en el diagrama se puso una sola para simplificarlo visualmente. Pueden realizar requests para validar efectivamente el stock, en caso de ser necesario. Es a través de la SPA y deben autenticarse.

## Página 5

### En cuanto a Availability

- Si se cae el backend: múltiples instancias con LB.
- Si se cae la DB: esquema primary-secondary.
- Cortes de servicios contemplados en el acuerdo con el datacenter.
- Ataque DDoS: WAF.
- Se supone que el servicio de los proveedores es altamente disponible.
- Se solicita disponibilidad del sistema de adquisiciones.
- Se solicita que la cola corra en cluster para eventuales caídas.
- Se solicita al almacén central doble proveedor de red y un generador para afrontar cortes.
- Se solicita que el mail service sea altamente disponible.

### En cuanto a Security

- Gestión de controles de acceso: ACL.
- Ataque MITM: uso de HTTPS.
- Robo de credenciales a médicos o gerentes: 2FA.
- Accesos indebidos a la DB: Encryption at Rest.
- Para una mayor capa de seguridad y privacidad, se usan conexiones mediante VPNs con los depósitos, proveedores y sistema de adquisiciones.
- Ataque DDoS: WAF (ya aclarado arriba).
- Solamente se permite a agentes del almacén central recibir el mail de notificación de que deben mandar suministros a un depósito; ellos lo gestionan. Para acceder, sus usuarios tienen 2FA.
- Los agentes de depósito son los únicos que pueden hacer requests para validar el stock, con su usuario (2FA), mediante la SPA.

## Página 6

### En cuanto a Interoperability

- Como los distintos proveedores tienen interfaces diferentes, se aplica un patrón adapter para realizar las comunicaciones.
- Se diseña e implementa el endpoint correspondiente para que los proveedores puedan enviar las notificaciones.

### En cuanto a Performance

- Se realizan consultas en paralelo a los proveedores aplicando multithreading para agilizar el proceso.
- Se guarda el stock centralizado en el sistema para que las consultas estén actualizadas con la información más reciente (real-time), sin tener que consultar a los depósitos.

### Ejercicio D

- **Riesgos:** se cae el LB; se cae el mail service.
- **No riesgos:** se cae una instancia del backend; se cae un nodo de la DB.
- **Supuestos:** los servicios brindados por los proveedores son altamente disponibles; el departamento de adquisiciones debe aprobar la compra y lo hace casi inmediatamente.
- **Tradeoffs:** Performance vs Security: Encryption at Rest brinda seguridad, pero agrega overhead sobre las operaciones. Availability vs Costos: tener replicaciones en el sistema brinda mayor disponibilidad, pero es más costoso.
