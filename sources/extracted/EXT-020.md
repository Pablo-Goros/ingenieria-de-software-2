Inge II - Cheatsheet

### Bucket de Soluciones

- Hosting: Existen distintas opciones de Hosting para nuestro sistema según el foco.

Cloud: Se deploya todo el sistema en tecnología cloud como AWS. Es una opción más barata y que permite aumentar el alcance de la solución (expandirse a otros países) de manera eficiente. Cortes de luz/internet o desastres naturales están contemplados, depende de los datacenter del servicio.

On Premise: Los servidores son propios de la empresa, y se pueden hostear tanto en un datecenter compartido como en el mismo edificio de la compañía. Sirve para incrementar el ownership del sistema, ya que se tiene total control de todas las características. Deben contemplarse casos de cortes en los servicios o desastres naturales (pueden requerirse prevenciones en caso de un datacenter compartido).

Salas Cofre: Son salas para almacenar los servidores y correr el sistema que se cierran literalmente con candado y nadie puede acceder. Tiene la misma característica de ownership que el caso anterior, y deben contemplarse también cortes y desastres.

- Múltiples Instancias de Backend + Load Balancer: Brinda escalamiento horizontal, permitiendo aumentar la capacidad de cómputo bajo demanda. Brinda disponibilidad y permite realizar procesamiento en paralelo, aumentando la performance. Tiene siempre el riesgo de la caída del Load Balancer, pero el No Riesgo de la caída de una instancia del Backend.

- Bases de Datos: Existen distintos tipos de bases de datos con diferentes esquemas y casos de uso. Es importante considerar el teorema CAP a la hora de elegir, y además, que las NoSQL nacieron en el contexto de big data, es decir, cantidades masivas de datos. Para casos de acceso normal, no intentar hacer un overkill con la solución.

SQL OLTP: este tipo de DBs son transaccionales y útiles para esquemas relacionales, donde se necesitan realizar, por ejemplo, funciones de agregación. Dentro del teorema CAP, es CA, por lo que brinda consistencia y disponibilidad, pero no tolera particiones.

SQL OLAP: son bases de datos también relacionales, pero para uso exclusivamente analítico (reporting). Se almacenan grandes volúmenes históricos desnormalizados (para no hacer joins) y se precalculan posibles agregaciones. Se generan a partir de procesos ETL (Extract, Transform, Load) desde otra base de datos, siempre agregando datos, nunca eliminando.

Caché: bases de datos volátiles que permiten a los sistemas acceder a información almacenada en memoria, aumentando notablemente el tiempo de respuesta. Tienen la contra de que son muy caras, por lo que no se pueden guardar grandes cantidades de información. Es importante aclarar qué se guarda y cuándo se invalida el dato.

Cassandra: es una base de datos columnar, que permite el manejo de cantidades masivas de lecturas y escrituras. Brinda disponibilidad y tolerancia a particiones, ya que corre en clúster y mantiene una comunicación entre los nodos mediante protocolo gossip, permitiendo escalar de manera horizontal fácilmente con el agregado de nodos. No brinda consistencia fuerte, por lo que no sirve cuando se requiere transaccionalidad.

MongoDB: es una base de datos orientada a documentos que brinda consistencia y tolerancia a particiones, pero no alta disponibilidad. Sirve cuando se requiere flexibilidad de esquema, y proporciona un alto volumen de escrituras con escalado horizontal mediante sharding y réplicas.

Objetos: son bases de datos para guardar objetos complejos en cualquier lenguaje de programación. Automatizan las operaciones más comunes (CRUD) y facilitan la programación, a costa de performance, y complejidad.

Además de estos tipos de bases de datos, se tienen dos esquemas para manejar distintos crecimientos en la demanda:

Primario-Secundario: busca escalar las operaciones de lectura. Sobre el nodo primario se aplican todas las escrituras, y estos cambios se envían en pseudo-tiempo real a N réplicas secundarias. Estas permiten lecturas en forma independiente. Ante la caída del nodo primario, los secundarios eligen uno para tomar su rol.

Primario-Primario: busca escalar las operaciones de escritura. Los N nodos, siendo primarios, aceptan tanto operaciones de lectura como escritura en forma concurrente. Esto trae problemas de concurrencia, por lo que no todos los motores de RDBM soportan este modo de operación. MySQL lo tolera con Group Replication; para Postgres se requieren extensiones. En todo caso se sacrifica la performance.

- Frontend: Para permitirle al usuario interactuar con el sistema, existen dos principales mecanismos de aplicación:

Webapp: es una aplicación donde el servidor procesa y genera un archivo HTML completo nuevo ante cada interacción del usuario, obligando al navegador a recargar la página entera en cada clic. El mecanismo de renderizado es Server-Side Rendering (SSR), ya que toda la lógica de procesamiento visual ocurre en el servidor. Suelen ser mejores para SEO (Search Engine Optimization), ya que la página aparece en los primeros resultados de Google de forma orgánica.

SPA: es una aplicación que carga un único archivo HTML inicial y utiliza JavaScript en el navegador para reescribir la pantalla de forma dinámica pidiéndole al servidor solo los datos estrictamente necesarios, sin recargar nunca la página. El mecanismo de renderizado es Client-Side Rendering (CSR), ya que el procesamiento visual se delega al dispositivo del usuario. Son ideales para interfaces interactivas.

- Queues: Una queue es una cola de mensajes que permite que un sistema emisor deposite mensajes de forma inmediata y se desentienda, para que uno o varios procesos secundarios (workers) los extraigan y procesen a su propio ritmo sin bloquear la conexión original del usuario. Un ejemplo muy usado es Kafka (en realidad es más que una queue), pero preferible definir los requisitos para una queue genérica, es decir, decir que se tomará una cola que cumpla con las características deseadas según el caso de la siguiente lista:

Correr en Clúster: debe permitir replicación de datos entre distintos nodos para que, si se cae un servidor, otro tome el control sin perder mensajes ni cortar el servicio.

Persistencia de Datos: si el clúster entero se apaga o se reinicia por un corte de energía, los mensajes no procesados deben seguir allí al levantar.

TTL para los Datos: debe proveer un mecanismo de limpieza automática, es decir que los mensajes deben expirar tras un tiempo determinado.

Garantías de Entrega: se debe poder escoger entre los siguientes modos de garantía de entrega:

At-most-once: El mensaje se entrega y, si el worker se cae mientras lo procesaba, el mensaje se pierde.

At-least-once: El mensaje se reenvía hasta que el worker confirma (ACK) que lo procesó con éxito. Puede generar duplicados si la red falla en el medio, por lo que exige que tus workers sean idempotentes.

Exactly-once: Garantiza que el mensaje se procese una única vez, coordinando transacciones entre la cola y el consumidor. Es el más costoso a nivel performance.

Ordenamiento de Mensajes: la queue debe permitir respetar un cierto orden entre los mensajes.

Dead Letter Queue: la queue debe poder detectar que un mensaje falló más de X veces consecutivas y, de forma automática, aislarlo enviándolo a una DLQ aparte.

- Seguridad y Conexiones: Todas las conexiones entre servicios y partes del sistema deben contemplar distintos casos de seguridad o posibles problemas que podrían surgir.

HTTPS: es la versión segura y cifrada de HTTP (protocolo de comunicación de la capa de aplicación que define el formato y las reglas para la transferencia de recursos) que utiliza algoritmos criptográficos (TLS/SSL) para proteger la confidencialidad e integridad de los datos.  Toda comunicación a través de internet debería utilizar HTTPS en los ejercicios.

JWT: es un estándar abierto que define un formato compacto y autónomo para transmitir información de forma segura entre partes como un objeto JSON, el cual consta de tres partes codificadas en Base64Url (Header, Payload y Signature) separadas por puntos, permitiendo que el receptor verifique la autenticidad e integridad de los datos mediante una firma digital sin necesidad de consultar una base de datos centralizada en cada petición. Es útil cuando se tiene comunicación con APIs

WAF: Es un servicio de seguridad perimetral que analiza, filtra y bloquea el tráfico HTTP/HTTPS malicioso dirigido específicamente hacia una aplicación web, protegiéndola contra ataques de la capa de aplicación como SQL Injection, Cross-Site Scripting (XSS) y DDoS (solamente de capa 7 en este último caso).

VPN: Es una tecnología de red que crea una conexión cifrada y segura (un túnel) sobre una infraestructura pública como Internet, permitiendo a los usuarios o sistemas remotos enviar y recibir datos como si estuvieran conectados directamente a una red privada local.

Websockets: Es un protocolo de comunicación bidireccional, full-duplex y persistente sobre una única conexión TCP, diseñado para permitir una interacción fluida y en tiempo real entre el navegador del cliente y el servidor sin la sobrecarga que genera el modelo tradicional de petición-respuesta de HTTP. Trae problemas de availability si se usa con un backend que corre en múltiples instancias, ya que si se corta la conexión por parte del nodo, no hay un mecanismo que tome esa conexión y responda.

Webhooks: Es un mecanismo de comunicación asincrónico basado en eventos mediante el cual una aplicación envía automáticamente datos en tiempo real a otra a través de una petición HTTP POST hacia una URL específica, en el preciso momento en que ocurre un suceso predefinido. No se puede usar con una SPA.

- Sistemas de Autenticación: Para la autenticación de usuarios, puede solicitarse una capa extra de seguridad además del login.

2FA: Es un subconjunto de MFA que exige estrictamente dos evidencias de categorías distintas (típicamente algo que sabés, como una contraseña, y algo que tenés, como un código de SMS o un token OTP) para validar la identidad de un usuario antes de concederle acceso al sistema.

MFA: Es el método de control de acceso e identidad más amplio que requiere dos o más factores de verificación independientes pertenecientes a categorías diferentes (conocimiento, posesión o inherencia/biometría) para robustecer la seguridad, garantizando que el compromiso de uno de ellos no baste para vulnerar la cuenta.

- Protección de Datos: Existen dos tipos de encriptación para los datos, según el momento en el que se los quiera proteger.

Encryption At Rest: Es la práctica de seguridad de cifrar los datos estáticos almacenados en un soporte físico o persistente (como discos duros, bases de datos, almacenamiento en la nube o backups) para garantizar que la información permanezca ilegible y protegida en caso de acceso físico no autorizado o robo del hardware de almacenamiento. Agrega overhead en las operaciones, ya que se debe desencriptar.

Encryption In Transit: Es la práctica de seguridad de cifrar los datos mientras se desplazan activamente a través de una red pública o privada (como internet o la red interna entre microservicios) utilizando protocolos seguros como TLS/SSL o SSH, evitando que atacantes intercepten, espíen o manipulen la información en movimiento. - Manejo de Datos Numéricos: En los casos donde surgen datos numéricos, como los tomados por sensores, se deben contemplar distintos aspectos de todo el proceso, como la recolección, el traslado y el almacenado.

Error de Punto Flotante: Es la imprecisión numérica que ocurre cuando un sistema informático intenta representar números decimales continuos (reales) usando un número finito de bits bajo el estándar IEEE 754, lo que provoca pequeños errores de redondeo o truncamiento debido a la imposibilidad de representar con total exactitud ciertas fracciones decimales en formato binario.

Punto Fijo: Es un método de representación numérica en computación donde la cantidad de dígitos asignados tanto para la parte entera como para la parte fraccionaria se mantiene estrictamente fija mediante una posición invariable de la coma decimal, lo que permite realizar operaciones matemáticas ultra rápidas utilizando la lógica interna de enteros a costa de sacrificar drásticamente el rango dinámico de los números que se pueden procesar. Agrega overhead en los cálculos.

Métodos Numéricos: son algoritmos matemáticos utilizados para aproximar de forma aritmética y computacional las soluciones a problemas analíticos complejos. Deben aplicarse cuando las ecuaciones subyacentes son imposibles de resolver de manera exacta o cuando solo se dispone de un conjunto finito de puntos de datos discretos (como las lecturas recolectadas por un sensor) que requieren ser interpolados o integrados en el tiempo.

Timeout (Polling): Cuando se está realizando polling de datos de un sensor por ejemplo, debe incluirse un timeout. Una opción es tomar el P90 (el 90% de las veces el sensor va a responder a tiempo) y multiplicarlo por 1,1 para evitar alertas falsas por cualquier pequeña fluctuación de la red. Si se cumple el timeout, el Poller no se traba ni rompe el sistema; simplemente skipea ese sensor en esa ronda de recolección, genera una alerta técnica (un log de error) para que soporte sepa que el sensor está fallando, y pasa inmediatamente al siguiente sensor.

Scheduling (Polling): Al tener una variedad de sensores, se pueda aplicar técnicas de scheduling (como en un sistema operativo) para el polling, logrando así distribuir de manera eficiente la cantidad de peticiones.

- Archivos: Existen casos donde se pueden tener almacenados archivos (como por ejemplo libros) y se necesita hacer una búsqueda eficiente, por ejemplo, por una palabra contenida.

Elastic Search: motor de búsqueda y analítica distribuido y construido sobre la biblioteca Apache Lucene, que está diseñado específicamente para almacenar, indexar y consultar grandísimos volúmenes de datos en tiempo real mediante una estructura de índice invertido. Es útil cuando se necesita implementar un buscador avanzado de texto libre en tiempo real que devuelva resultados inmediatos por cualquier palabra clave, o bien para almacenar, indexar y analizar de forma masiva logs técnicos y métricas de infraestructura. Es importante que NO guarda los archivos, sino la indexación correspondiente.

- Patrones: es una solución conceptual, probada y reutilizable a un problema común y recurrente que surge dentro de un contexto determinado en el diseño de software.

Patrón Adapter: patrón de diseño estructural que actúa como un intermediario o traductor para permitir que dos interfaces incompatibles se comuniquen y trabajen juntas sin necesidad de modificar su código fuente original. Agrega cierto overhead en las operaciones, ya que toda capa de abstracción añade un costo computacional.

Patrón Reactor: consiste en tener un thread constantemente polleando y, cuando tiene un dato, lo carga en una cola de trabajo, donde luego es levantado por otro thread. Es útil en casos como por ejemplo el de un poller, para aprovechar el multithreading.

Patrón Publish-Subscribe: patrón de arquitectura de mensajería donde los emisores (publicadores) envían mensajes a un componente intermediario (topic o broker) sin saber quiénes los van a recibir, permitiendo que múltiples receptores (suscriptores) interesados consuman dichos mensajes de forma asincrónica y desacoplada.

Patrón MVC: patrón de arquitectura que separa una aplicación en tres componentes independientes: el Modelo, que gestiona los datos y las reglas de negocio; la Vista, que representa la interfaz de usuario; y el Controlador, que gestiona las peticiones del usuario e interconecta a ambos. Es útil al desarrollar aplicaciones interactivas de escritorio o web tradicionales donde se requiere separar netamente la interfaz visual de la lógica de negocio

Patrón de Prevalencia: cada vez que hay un cambio en la estructura de datos, toma un snapshot y baja a disco toda esa información.

### Availability

- Ataque DDoS → Web Application Firewall (WAF)

- Caída Backend → Múltiples Instancias + Load Balancer

- Caída Base de Datos → Replicación Primaria-Secundaria si es relacional o Funcionamiento en Clúster para no relacionales.

- Corte de Internet → Múltiples Proveedores

- Caída de la cola → Asegurarse de especificar que corra en clúster

- Corte de luz → Generador o doble servicio de luz

- Caída de Internet → Doble proveedor

### Security

- Ataque DDoS → Web Application Firewall

- Ataque MItM → Conexiones HTTPS

- Ataque a operadores con info privilegiada → Usar VPNs en sistemas internos

- Robo de credenciales → Multi Factor Authentication (MFA)

- Gestión de Accesos → Access Control List (ACL) en el Backend

- SQL Injections → Sanitizar entradas en la SPA.

- Ingresos maliciosos a la BD → Encryption at rest, la data se guarda encriptada.

- Datos muy sensibles → Hosting privado en una sala cofre (solamente se accede con llave)

### Performance

- Las lecturas tardan mucho → Caché en el back. Importante definir qué se guarda y cuándo se borra.

- Demasiadas solicitudes → Proceso en paralelo (sirve tener muchas instancias) y multithreading.

- Reportes Real Time → Réplica de sólo lectura de la base de datos

- Reportes No Real Time → Se copian los datos de la BD SQL OLTP a una OLAP mediante ETL (Extract, Transform, Load). Hacer el reporte en horarios de baja demanda.

-  Caída del elemento activo → Tener un heartbeat entre instancias para saber cuándo usar las pasivas.

- Lectura en real time → websocket

- Búsquedas en múltiples fuentes → procesamiento asincrónico y en paralelo con un timeout.

### Precision

- Error de Punto Flotante → punto fijo

- Sensor puede medir mal → dos en activo-activo

- Propagación de errores en cálculos intermedios → métodos numéricos

- Faltan mediciones → interpolación de datos

- Mediciones varían mucho → Intervalos de confianza

- Guardar datos como string en la base de datos

### Scalability

- Picos Recurrentes → Load balancer

- Muchos accesos a la SPA desde distintos puntos → hosting en CDN

- Bases de datos que permitan sharding y, por ende, escalamiento horizontal.

- Crecen las lecturas → read replicas

### Interoperabilidad

- Patrón adapter: patrón de diseño estructural que permite la colaboración entre objetos con interfaces incompatibles, actuando como un traductor que convierte la interfaz de una clase existente en otra interfaz que el cliente espera.

- Exponer una API con requests que sólo toleren lecturas para que otros servicios puedan integrar.

### Fault Tolerance

- Fallo en la carga de un archivo necesario para generar un reporte → el sistema sigue funcionando normalmente basándose en la información disponible.

### Accessibility

- Probar con distintos usuarios

- Internacionalización

- Diseños HCI

- Alt en imagénes para lectores de pantalla

- Sistemas de lectores de pantalla

### Tradeoffs Comunes

- Availability vs Costos al tener escalamiento horizontal

- Performance vs Security al tener encryption at rest

- Precision vs Performance si se tienen operaciones de punto fijo

- Performance vs Availability si se tienen websockets, ya que si se cae un nodo, ningún otro toma la conexión y se muere.
