Gestión de Calidad
● Conceptos clave:
○ La gestión de calidad en software busca asegurar que los procesos de desarrollo cumplan con
estándares deﬁnidos para garantizar la calidad del producto ﬁnal.
○ Concepto complejo y de aristas múltiples (puntos de vista).
● Importancia:
○ Reduce errores en etapas tempranas del desarrollo.
○ Mejora la satisfacción del cliente.
○ Incrementa la eﬁciencia y la sostenibilidad del software.
● Métricas de calidad:
○ Densidad de defectos.
○ Tasa de errores por usuario.
○ Tiempo medio para la resolución de problemas.

## Page 9

Calidad - Costo de Calidad y "No Calidad"
● Costo de calidad (CoQ): Se reﬁere a los gastos necesarios para prevenir defectos y garantizar un producto de
alta calidad.
○ Ejemplo: Entrenamiento, revisiones, auditorías.
● Costo de "no calidad": Gastos derivados de errores o fallos en el producto.
○ Fallos internos: Reparaciones previas al lanzamiento.
○ Fallos externos: Reclamos de clientes, pérdidas de reputación.
● Conclusión: Invertir en calidad reduce signiﬁcativamente los costos de "no calidad".

Caso especial de "No Calidad": Deuda técnica
Deﬁnición: la deuda técnica es el costo de retrabajo que
aparece cuando se prioriza una solución rápida por sobre la
más efectiva.
Origen y analogía: el término lo acuñó Cunningham* (1992) y
se compara con la deuda ﬁnanciera: puede ser “buena” si se
gestiona, o “mala” si se ignora.
Cuadrantes de Fowler*: prudente + deliberada, imprudente +
deliberada, prudente + inadvertida, imprudente + inadvertida;
sirven para calibrar intención y nivel de riesgo.
Origen: puede ser funcional o tecnológica
* Howard Cunningham: XP, Maniﬁesto Ágil, Wiki
* Martin Fowler: “Refactoring: Improving the Design of Existing Code” 10

(“nadie podía preverlo”)
Se trabajó con buenas

que obliga a reescribir gran parte de la lógica.

(“no sabíamos que era

Falta de conocimiento o
control; la deuda surge sin que
el equipo se dé cuenta.

## Page 14

Caso especial de "No Calidad": Deuda técnica
Tipos según Steve McConnell (autor de “Code complete”):
● Intencionada: decisión consciente de optimizar el presente (puede ser a corto o largo plazo).
○ Ejemplo: elegir un framework rápido pero de bajo rendimiento para llegar a un deadline; requerirá
reescritura posterior.
● No intencionada: errores, falta de conocimiento o diseño defectuoso.
○ Ejemplo: liberar código escrito por desarrolladores junior sin revisión suﬁciente, generando errores que
aparecen tras el lanzamiento.
Buenas prácticas de control:
● Registrar cada deuda en un sistema de seguimiento/backlog con esfuerzo y fecha estimada.
● Tratarla como historias de usuario (en enfoques ágiles); si supera 90 días, marcarla como crítica.
● Fomentar transparencia y comunicación: pagar la deuda en incrementos pequeños y visibles para todo el
equipo.

## Page 29

Casos de Prueba de Software: pasos especíﬁcos para probar una funcionalidad o característica del software.
Incluye precondiciones, datos de entrada, resultados esperados y obtenidos, para garantizar que cada componente
funcione como se espera. Incluye el registro y trazabilidad de las pruebas.
Objetivo:
● Veriﬁcar que cada requisito de negocio se cumpla sin errores.
● Detectar defectos antes de la puesta en producción, reduciendo costo de corrección.
● Servir como documentación viva que facilita mantenimiento y regresión.
Buenas prácticas de redacción:
● Claridad: una sola veriﬁcación por caso; evita ambigüedad.
● Trazabilidad: referencia al ID del requisito o user story.
● Atomicidad: los casos no deben depender unos de otros.
● Datos realistas: usa entradas representativas (y evita información sensible).
● Resultados observables: deﬁne salidas medibles (UI, API response, BD, logs).
● Mantenibilidad: usa nombres descriptivos y versiona los casos junto al código.

## Page 32

¿Qué es?
● Plantilla de Behavior-Driven Development que conecta requisitos de negocio con pruebas ejecutables.
● Favorece lenguaje comprensible para negocio, QA y desarrollo.
Estructura
Given (contexto): estado previo del sistema y datos iniciales.
When (acción): evento/disparo que el usuario o sistema realiza.
Then (resultado): salida observable o cambio esperado.
Buenas prácticas
● Una sola acción principal por escenario.
● Evitar condicionales: usar escenarios separados para ramas positivas y negativas.
● Mantener las frases en tiempo presente y voz activa (el sujeto realiza la acción).

## Page 34

¿Dónde puedo usar Given-When-Then?
● Historias de usuario → se convierte en los criterios de aceptación que validan el “Deﬁnition of Done”.
● Casos de uso → cada ﬂujo (principal o alternativo) puede desglosarse en uno o varios escenarios G-W-T.
● Tareas / subtareas técnicas → útil para describir comportamiento observable de un endpoint, script o
micro-servicio.
● Requerimientos sin formato estándar → el template impone estructura y hace la especiﬁcación testeable.
● Reglas de negocio → explicita condiciones y resultados, evitando ambigüedad entre áreas de negocio y
desarrollo.
● Requerimientos no funcionales medibles (p. ej. performance, seguridad) → “Given carga de 100 TPS… Then
tiempo < 2 s …”.
