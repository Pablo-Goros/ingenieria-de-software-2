CMS (P - 1C2021)

Un cliente nos pide la realización de un sistema para publicación de contenidos. Será usado como base de conocimiento para su empresa, y la idea del sistema es que los usuarios finales puedan entrar a esta plataforma para buscar información. Se conocen, por ahora, varios tipos posibles de usuarios: redactores, editores, administradores, y usuarios finales.

El usuario final quiere buscar información. La información debe ser relevante, precisa y ser encontrada inmediatamente por cualquier palabra del documento (no sólo el título). Una vez encontrada la información, el usuario la querrá leer, imprimir y marcar como favorita. Puede comentar en los documentos y darle un “rating”. La búsqueda debe ser posible desde dispositivos variados, como ser “kiosks” en las salas de uso común de la empresa, estaciones de trabajo, o tablets de los usuarios finales.

El redactor quiere crear contenido. El sistema, como plataforma, debe facilitar esta actividad mediante la provisión de herramientas de corrección, y de guardado de apuntes. Los artículos escritos pasan a un estado de “borrador”, para ser aprobados a su publicación. El editor necesita poder ver los artículos en borrador, aprobarlos o pedir cambios, mediante “workflows”. Todo cambio debe registrarse. El editor es quien publica. El administrador maneja el “back-office”, y para ello necesita crear y borrar usuarios y proveer moderación a los comentarios.

El sistema debe proveer a los distintos usuarios reportes de acuerdo a sus necesidades: esto incluye reportes uso del sistema, de rating de artículos, de tiempo promedio a publicación, etc. El sistema maneja todo el ciclo de vida de los artículos, y por lo tanto debería ser posible manejar un log de uso para que cualquier cambio sea auditable.

A partir de su puesta en funcionamiento, y luego de un proyecto de migración, el sistema será la única fuente de datos para todos los procesos de la empresa, volviendo obsoleta la documentación en papel, y a múltiples sistemas existentes. Por lo tanto, entre otras cosas, se espera que exista resistencia al cambio en los usuarios.

El sistema debe ser cubierto con un presupuesto razonable, sin gastos superfluos de infraestructura o desarrollo, ya que debe quedar dinero para la migración y entrenamiento.

Se divide el sistema en dos partes, para una separación de responsabilidades y acciones entre los usuarios comunes (publicadores y lectores) y los administradores del sistema (principalmente por seguridad). Ambos tienen un mismo codebase, para generar un ahorro en desarrollo, tal como se solicita, pero se generan dos artefactos de ejecución independientes. Logística (P - 1C2021)

El cliente, una empresa de logística nacional, pide la construcción de un sistema que provea información posicional de sus móviles.

El sistema deberá proveer, como principal función, una vista del mapa de la República Argentina y países limítrofes, con la ubicación en tiempo real de cada cargamento. Este mapa debe ser de fácil filtrado por conductor, carga, valor transportado, tiempo a destino y condiciones del contrato. Cada móvil se verá como un punto en el mapa, que cambia de color según el estado.

La ubicación de cada carga se obtiene de un GPS ubicado en el container, en el momento de despacho. Este GPS se contrata a otra empresa, que provee un servicio JSON a través del cual se puede pedir el estado y ubicación de un móvil, dado un ID. Este ID es ingresado al sistema por el operario que autoriza la salida del camión en cada almacén, previo chequeo de la carga.

La información original de cada móvil deberá provenir del sistema interno de ventas, que almacena el contrato, y del sistema de la aduana argentina, que provee la información de cargas ingresadas al país. Se sabe que ambos sistemas cuentan con algún tipo de conectividad, pero no hubo tiempo de investigar a fondo.

El operario del despacho también debe poder imprimir una hoja de ruta para el chofer al momento de autorizar la salida del cargamento. Esta hoja será entregada al operario de destino y en los pasos intermedios (distribuidos en todo el país), y cada operador asentará en el sistema el pasaje del móvil.

El control de móviles es realizado por un equipo de operadores en simultáneo, cada cual marca una serie de móviles a seguir. De esta manera, las alarmas y más novedades, son informadas al operador adecuado. El sistema debe soportar alarmas por móvil, que sean configurables para casos diversos: móvil detenido más de X minutos, móvil fuera de ruta, etc. La empresa se compromete a este control por medio de un SLA con sus clientes y con su propia aseguradora.

El gerente de operaciones debe poder obtener un reporte diario con las novedades de importancia del día anterior. El reporte lo tiene que poder abrir con el Excel.

El sistema debe controlar el tiempo en movimiento de cada móvil, ya que una vez al mes deberá exportar esta información al sistema de nómina, para el pago de horas extras de cada chofer.

### Ejercicio C

La arquitectura candidata es la siguiente:

Aclaraciones:

La base de datos SQL OLTP se utiliza para guardar datos relacionados con los operadores, containers y demás información necesaria para la operatoria del sistemas, así como también registros de logs para realizar auditoría. Sobre los datos necesarios, se realizan operaciones ETL para volcarlas en una SQL OLAP y generar posteriormente reportes.

El hosting del sistema se realizará en un espacio alquilado dentro de un datacenter con equipos propios, para preservar la seguridad de los datos y el ownership del sistema. Se analizará en el contrato que las instalaciones cuenten con previsión de casos de corte de luz, cortes de  internet y desastres naturales. Al ser un servicio para Argentina y países limítrofes, la degradación en performance por latencia es mínima.

El frontend con el mapa para los operarios consta de una SPA, por lo que las conexiones serán stateless.

El sistema de monitoreo de los operarios se realizan mediante polling con una tasa de request por cada 3 segundos, ya que no es tan importante que vean la posición en todo momento, sino poder ir observando la ruta que toman.

Las alarmas y novedades del sistema se envían a los operarios mediante un servicio de mailing. Una vez que el sistema los registra, los ingresa en una cola para enviar estas notificaciones por mail. Es necesario que la cola corra en clúster para afrontar caídas y que tenga persistencia de datos, para que no se pierdan mensajes que el servicio de alertas puede fallar en enviar.

En cuanto a Availability:

Ataque DDoS → WAF

Caída del backend → múltiples instancias con un load balancer.

Caída de la base de datos relacional → esquema primario secundario.

Caída de la base de datos Cassandra → corre en clúster.

Caída de la queue de notificaciones → corre en clúster.

Se asume que el servicio de GPS es altamente disponible.

Se cae el servicio de alertas → corre en clúster.

En cuanto a Performance:

Las conexiones con el sistema de GPS se realizan a través de websockets para garantizar real time en el guardado de datos.

Todos los datos recibidos del sistema de GPS se guardan en un clúster Cassandra, que tolera cantidades masivas de escrituras y lecturas de datos, además de ser AP bajo el teorema CAP.

Las operaciones ETL para generar la información guardada en la base de datos OLAP se realizan en momentos de bajo uso del sistema, para no ocasionar una sobrecarga.

Se agrega una caché con los datos de los contenedores en movimiento, buscando acelerar la obtención de sus datos relacionados para las distintas operaciones. Se invalida una vez que se marca que el container llegó a destino.

En cuanto a Security:

Las conexiones con los servicios tanto internos como externos se realiza a través de una VPN.

Se incluye un WAF para prevenir ataques DDoS.

Todas las comunicaciones a través de internet se realizan a través de HTTPS para prevenir un ataque MITM.

El backend cuenta con un Access Control List para gestionar el acceso de los operadores al sistema y sus distintos niveles.

Los operadores requieren autenticarse mediante un MFA, para prevenir los robos de credenciales.

Se aplica encryption at rest para los datos guardados en la base de datos SQL OLTP, sacrificando performance pero brindado mayor protección.

Auditability:

Se guardan registros de los cambios realizados por los operarios en una tabla de logs dentro de la base de datos OLTP SQL.

Se guardan todos los recorridos de los contenedores para poder cruzar los datos y obtener trazabilidad.

### Ejercicio D

Riesgos: Se cae el Load Balancer, se cae la API de GPS.

No Riesgos: Se cae una instancia del backend, se cae un nodo de la base de datos Cassandre.

Supuestos: El servicio de GPS provisto es altamente disponible, todos los operarios tienen dispositivos móviles para recibir alertas y todos los pasos intermedios tienen acceso a internet para conectarse al sistema y asentar el pasaje.

Tradeoffs: Performance vs Security - encryption at rest aumenta el tiempo de respuesta al usuario. Availability vs Costo - el escalamiento horizontal brinda la capacidad de aumentar el cómputo dinámicamente pero tiene un costo mayor.

Bibliotecas Nacionales (P - 1C2022)

Se ha abierto una licitación para un sistema de catálogo para bibliotecas nacionales. El objetivo principal de este sistema es que todo usuario pueda realizar búsquedas de libros, en la biblioteca y desde sus casas. Este nuevo sistema será el punto obligado de entrada de toda búsqueda y reserva de libros, y como tal, la caída del sistema obliga a la biblioteca a cerrar por el día. Téngase en cuenta que el sistema debe adecuarse al mínimo denominador tecnológico posible (no se puede hacer una inversión tecnológica grande), pero soportar el mayor espectro posible de sistemas cliente y usuarios.

El sistema debe permitir buscar libros rápidamente, otorgando un listado en pocos segundos. La búsqueda debe permitir no sólo títulos, sino autores, ISBN, texto de la sinopsis y número de catálogo. Si el libro no se encuentra en la biblioteca, debe sugerir otra biblioteca donde sí se encuentre en catálogo en ese momento. De existir el libro en catálogo, el sistema debe permitir el préstamo o la reserva según corresponda. Las búsquedas las pueden hacer todos los usuarios, las reservas sólo son permitidas en persona, y realizadas por un bibliotecario.

Adicional a los libros, el sistema debe poder comunicarse con otras fuentes de datos, de diarios y revistas internacionales de divulgación, así como de otras bases de datos internacionales que puedan ir surgiendo en base a acuerdos. No se conocen en este momento las APIs de cada sistema, sólo que son en tiempo real. En un corto plazo, se quiere habilitar una API propia, para que bibliotecas extranjeras puedan comunicarse con el catálogo nacional, y debe ser contemplado.

Los bibliotecarios deben poseer una interfaz de carga de datos, así como la posibilidad de extraer reportes de libros consultados. Estos reportes deben permitir cruzar datos de todas las bibliotecas alcanzadas por el sistema.

### Ejercicio B

Arquitectura Candidata:

Aclaraciones:

La base de datos SQL OLTP guarda la información correspondiente a las reservas.

Como se cuenta con un presupuesto acotado y dada la naturaleza de los datos, se adoptará un hosting cloud, ya que no requiere de la inversión inicial en todos los equipos, y brinda un nivel de disponibilidad suficiente. No se deben tener en cuenta cortes de luz o internet ni catástrofes naturales para el servidor y, por ende, la búsqueda remota, pero para el caso de las reservas, que se hacen desde la biblioteca, se debería contar con un doble proveedor de internet y pensar en la opción de un generador, que igualmente representa un costo menor que la inversión en los equipos necesarios para hostear un sistema de biblioteca nacional.

Los datos de las bases de SQL se guardan cada períodos de cierto tiempo en la OLAP para generar los reportes, luego de la aplicación de las operaciones ETL.

Las consultas a otros sistemas se realizan asincrónicamente y en paralelo, por lo que no se espera a que todas respondan. Se otorga un timeout de 3 segundos, para respetar la performance establecida por la consigna. Los títulos recibidos se almacenan en una memoria caché, para en caso de llegar alguna petición por el mismo título, lograr devolver la misma biblioteca del caso anterior. Se invalida luego de pocos minutos, ya que puede ser quitado del catálogo por la otra biblioteca.

Se tienen tanto la SPA para el usuario como la interfaz (también una SPA pero separada) hosteadas en cloud al igual que el backend, pero no en un CDN dado que es un servicio nacional y se quiere ahorrar.

Las conexiones con los usuarios y bibliotecarios son mediante HTTPS para garantizar confidencialidad en la comunicación. Lo  mismo para la API que expondrá la biblioteca, ya que los requests llegarán a través de internet protegidos.

El backend posee un ACL para gestionar el control de accesos.

En cuanto a Availability:

Si se cae el backend → múltiples instancias con Load Balancer

Si se cae la base de datos → replicación primario-secundario

Ataque DDoS → WAF previo al LB.

Si se cae el load balancer, es muy complejo agregar otro y tarda muy poco para resetearse, por lo que se acepta el riesgo.

En cuanto a Performance:

Se realizan búsquedas paralelas y asincrónicas para libros que no estén en el sistema con un timeout de tres segundos para mantener la performance. Para esto, se asume que no existe una central donde se pueda buscar para todas las otras bibliotecas.

Se agrega una caché para los libros que no están en el catálogo pero sí en otras bibliotecas (indicando cuál o cuáles), para no tener que volver a realizar una búsqueda por todas las bibliotecas. La caché se invalida luego de unos minutos, para evitar inconsistencias con el catálogo de las otras bibliotecas.

En cuanto a Interoperability:

Las interfaces de las bibliotecas o servicios externos son incompatibles → se aplica un patrón adapter.

Para exponer servicios en un futuro, se debe agregar una API que permita únicamente lecturas.

En cuanto a Accessibility:

Se debe desarrollar una interfaz HCI friendly, contemplando el rango etario y los distintos perfiles que usarán la aplicación, pues recordemos que es un sistema nacional.

Realizar pruebas previas al lanzamiento con distintos tipos de usuarios que utilizarán la aplicación.

Agregar la descripción de imágenes (“alt”) para aquellos usuarios que ingresen con algún motor de ayuda dada sus capacidades.

Se podría contemplar el agregado de motores de lectura de pantalla para aquellos usuarios con discapacidad visual.

Sistema Integral de Atención (R - 2C2022)

Una empresa de telecomunicaciones desea mejorar significativamente la atención al público a través de sus canales: call center, web y chatbot. Para lo cual nos ha encargado el desarrollo de un sistema integral de atención (SIA).

Los procesos que debe cubrir el SIA son: administración de clientes (altas, bajas, modificaciones), consultas de facturación y pago, consultas de consumos, altas y bajas de servicios (incluyendo la instalación del servicio en casa del cliente), consulta de deuda y pago online/telefónico, reclamos técnicos (problemas con algún servicio de un cliente), ventas de nuevos servicios a un cliente. En el caso de recibir un reclamo, se debe proveer una funcionalidad de seguimiento del mismo, con notificación al cliente durante las diversas etapas.

El SIA debe estar operativo 24x7, y mantener un tiempo de respuesta adecuado, aún en momentos pico tales como problemas generales con algún servicio o problemas en la facturación.

Para brindar su funcionalidad, el SIA deberá interactuar con todos los sistemas de la compañía: sistema de clientes, sistema de ventas, sistema de facturación, sistema de recaudación, sistemas técnicos (uno para cada producto), sistemas de servicio técnico. Dado que la compañía tiene una estrategia de adquisición de nuevas compañías de telecomunicaciones, se espera que haya nuevos sistemas (no conocidos a la fecha) que haya que integrar en el futuro.

Los agentes del call center deben tener pantallas que integren toda la información del cliente y que permitan responder con rapidez las consultas, sin necesidad de poner al cliente “en espera”.

Los chatbots, así como el call center y la web, elaboran sus respuestas en función de las APIs y datos de los sistemas de la compañía.

Para fines de marketing, se desean consultar las interacciones con los clientes, mediante reportes diarios, pero también con la posibilidad de que analistas de marketing elaboren consultas ad hoc.

La cantidad estimada de clientes de la compañía es aproximadamente 5M, y crecerá con las adquisiciones futuras; sus servicios incluyen telefonía básica, internet, televisión por cable y conectividad empresarial para PYMEs.

Las ambulancias deben poder aceptar la emergencia.

Capacidad de incluir y quitar móviles.

Comunicación entre ambulancia y el sistema de monitoreo.

Se debe proveer una API para integrarse.

Debe incluir sistema de ruteo.

Visualización en Real Time.

Búsqueda de móviles por filtro.

### Ejercicio B

Atributos de calidad candidatos:

Availability: El sistema debe presentar alta disponibilidad para atender los pedidos del call center y contactar a las ambulancias.

Fault Tolerance: Una falla en el sistema de alertas no debe alterar el funcionamiento del sistema de monitoreo.

Interoperability: Se debe proveer integración con proveedores de servicios de salud, y con la API de ruteo del GCBA.

Performance: Se debe responder rápidamente a las consultas del call center para conseguir ambulancias, ya que la vida del paciente depende de esta velocidad.

Scalability: El sistema debe atender picos en las demandas de ambulancias, por ejemplo frente a epidemias.

Security: El sistema maneja datos sensibles, como historias clínicas de los pacientes, por lo que debe ser robusto en su seguridad.

Atributos definitivos:

Reliability

Performance

Interoperability

Security
